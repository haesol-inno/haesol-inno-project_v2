평가 항목 2(코드 구조 및 설계), 3(핵심 기술 원리), 4(심층 인터뷰)에 대한 설명을 코드 위치와 함께 정리했습니다.

## 1. 코드 구조 및 설계

### 1-1. 함수 분리 기준과 각 함수의 역할

**기준: "메뉴 하나 = 함수 하나", 그리고 두 번 이상 쓰이는 동작은 도우미 함수로 뺀다.**

- **메뉴 기능 함수**: 메뉴 번호마다 하나씩 있습니다 (`add_prompt`, `show_list`, `show_by_category`, `search_prompt`, `show_detail`, `toggle_favorite`, `show_favorites`, `export_markdown`, `edit_prompt`, `delete_prompt`, `show_top`).
  모두 `prompts` 리스트 하나만 받고, **데이터를 바꿨으면 `True`를 반환**합니다. `main()`은 `True`일 때만 파일에 저장합니다.
  그래서 각 기능은 "저장"을 신경 쓰지 않고, 저장 규칙은 `main()` 한 곳에만 있습니다.
- **입력 검증 함수**: `input_non_empty`, `input_number`, `confirm`, `input_or_keep`, `choose_category`, `select_prompt`.
  추가·상세·즐겨찾기·수정·삭제가 모두 "번호를 입력받아 프롬프트 고르기"를 하므로 `select_prompt` 하나를 같이 씁니다.
- **조회·출력 도우미**: `find_prompts(prompts, condition)`가 "조건에 맞는 프롬프트를 전체 목록 번호와 함께" 돌려주고,
  카테고리 조회·검색·즐겨찾기 목록·Top 목록은 조건(`lambda`)만 다르게 넘깁니다. 출력 형식은 `print_prompt_line` 한 곳에서 정합니다.
- **저장·내보내기 함수**: 파일을 다루는 코드(`load_prompts`, `save_prompts`, `export_markdown_files`)는 화면 입출력과 분리해서,
  테스트에서 임시 폴더 경로만 바꿔 바로 검사할 수 있게 했습니다.

### 1-2. 프롬프트 데이터 구조

```python
prompts = [                       # 리스트: 등록 순서 = 화면 번호
    {                             # 딕셔너리: 프롬프트 1개
        "id": 1,                  # 내부 고유 번호
        "title": "회의록 3줄 요약",
        "content": "...",
        "category": "학습/요약",
        "favorite": True,
        "views": 3,               # 상세 보기 조회수
    },
]
```

- 번호로 접근: 화면 번호 `n` → `prompts[n - 1]` (`select_prompt`)
- 필드 접근: `prompt["title"]`, `prompt["favorite"] = not prompt["favorite"]`
- 새 프롬프트는 항상 `make_prompt()`로 만들어서 필드가 빠지는 일이 없게 했습니다.
- 기본 데이터 `DEFAULT_PROMPTS`는 직접 수정하지 않고 `create_default_prompts()`로 복사해서 씁니다.

### 1-3. 입력 검증 위치와 동작

| 검증 | 위치 | 동작 |
|---|---|---|
| 빈 값 | `input_non_empty()` | `strip()` 후 비어 있으면 안내하고 **다시 입력받음** (while 반복) |
| 숫자 아님 / 범위 밖 | `input_number(message, min, max)` | `int()` 실패(`ValueError`) 또는 범위 밖이면 안내 후 **`None` 반환** |
| y/n | `confirm()` | y/yes, n/no 외에는 다시 입력받음 |
| 메뉴 번호 | `main()` → `find_menu_handler()` | `MENU_ITEMS`에 없는 번호면 안내 후 메뉴로 돌아감 |
| 중복 제목 | `check_duplicate_title()` | 공백·대소문자를 정규화해 비교, 같으면 저장 여부를 물음 |
| 저장 파일 형식 | `normalize_prompts()` | 리스트인지, 필수 필드가 문자열인지 검사, 빠진 선택 필드는 기본값으로 채움 |

`input_number`가 `None`을 돌려주면, 카테고리 선택(`choose_category`)은 `continue`로 다시 묻고,
나머지 메뉴 기능은 아무것도 바꾸지 않고 메뉴로 돌아갑니다. 검증 로직이 함수 몇 개에 모여 있어서 각 기능 코드에는 `if ... is None: return False` 한 줄만 있습니다.

### 1-4. 커밋을 나눈 기준

**"실행해서 확인할 수 있는 기능 하나가 완성되면 커밋"** 했습니다.
메뉴 루프 → 추가 → 목록 → 카테고리 → 검색 → 상세 → 즐겨찾기 → 즐겨찾기 목록 → 저장 → 내보내기 → 수정/삭제 → 조회수 → Top 순서이고,
각 커밋 시점에서 프로그램이 항상 실행되는 상태입니다. 커밋 성격은 `feat:`/`test:`/`docs:`/`chore:`/`merge:` 접두어로 구분했습니다.

## 2. 핵심 기술 원리

### 2-1. 리스트와 딕셔너리를 선택한 이유

| | 리스트 (`prompts`, `CATEGORIES`) | 딕셔너리 (프롬프트 1개) |
|---|---|---|
| 선택 이유 | 등록 순서가 유지되고, 화면 번호를 인덱스로 바로 쓸 수 있음. `append`/`remove`로 추가·삭제가 쉬움 | 값에 이름(`title`, `views`…)이 붙어 코드가 읽기 쉬움. 필드 추가(보너스의 `views`)가 쉬움 |
| 단점 | 제목으로 찾으려면 전체를 훑어야 함(O(n)). 삭제하면 뒤 번호가 당겨짐 | 키 이름 오타는 실행해야 발견됨. 순서 개념이 약함 |
| 이 프로그램에서 | 데이터가 수십~수백 개라 전체 순회 비용은 문제가 안 되고, 삭제 시 번호 변경은 안내 메시지로 알림 | 오타 위험은 `make_prompt()` 한 곳에서만 딕셔너리를 만들게 해서 줄임 |

"제목 → 프롬프트" 딕셔너리로 저장하지 않은 이유: 제목이 같은 프롬프트를 허용할 수 있어야 하고, 화면에 보여줄 순서가 필요하기 때문입니다.

### 2-2. 메뉴 반복에 while을 쓴 이유와 종료 조건

- 사용자가 몇 번 메뉴를 고를지 미리 알 수 없으므로 횟수가 정해진 `for`가 아니라 `while True`를 썼습니다.
- 종료 조건은 **`0` 입력 → `break`** 단 하나입니다. 메뉴 정의(`MENU_ITEMS`)에는 0번이 없어서 다른 기능과 섞이지 않습니다.
- 그 밖의 종료: `Ctrl+C`(`KeyboardInterrupt`)나 입력 끝(`EOFError`)은 `if __name__ == "__main__":`에서 잡아 메시지만 출력하고 끝냅니다.
  데이터는 바뀔 때마다 이미 저장되므로 이런 식으로 끝나도 잃어버리는 데이터가 없습니다.
- 잘못된 번호는 `continue`로 다음 반복으로 넘어가서 메뉴를 다시 보여줍니다.

### 2-3. "제목 또는 내용 포함" 검색 구현

```python
def matches_keyword(prompt, keyword):
    keyword = keyword.lower()
    return keyword in prompt["title"].lower() or keyword in prompt["content"].lower()
```

- 문자열의 `in` 연산자로 **부분 문자열 포함** 여부를 검사합니다.
- 키워드와 필드를 모두 `lower()`로 바꿔 영문 대소문자를 무시합니다 (`PANDAS`로 `pandas` 검색 가능).
- `or`로 제목과 내용 중 하나만 맞아도 결과에 포함합니다.
- `find_prompts(prompts, lambda prompt: matches_keyword(prompt, keyword))`로 걸러서, 결과에 **전체 목록 기준 번호**가 그대로 보입니다.

### 2-4. 브랜치를 나눈 이유와 병합 기준

- **이유**: 작업 브랜치는 항상 실행 가능한 상태로 두고, 새 기능은 `feature/*` 브랜치에서 따로 만들어
  만드는 도중의 코드가 다른 기능에 영향을 주지 않게 했습니다. 기능 단위로 이력을 볼 수 있고, 문제가 생기면 그 브랜치만 되돌리면 됩니다.
- **병합 시점/기준**: (1) 그 브랜치의 기능이 모두 완성되고 (2) 직접 실행해 정상·잘못된 입력을 확인하고 (3) 기존 메뉴도 그대로 동작할 때 병합했습니다.
- `--no-ff`로 병합해서 `git log --graph`에 기능 묶음이 갈라졌다 합쳐지는 모양으로 남게 했습니다 ([05_git_log.txt](logs/05_git_log.txt)).

## 3. 심층 인터뷰

### 3-1. 종료해도 데이터가 유지되게 하려면? → 구현함 (보너스 1)

- **설계**: 시작할 때 `load_prompts()`로 파일에서 읽고, 데이터가 바뀐 메뉴 직후 `save_prompts()`로 저장합니다.
- **형식: JSON**. 이유는
  1. 프로그램의 "딕셔너리의 리스트" 구조와 1:1로 대응해서 변환 코드가 거의 필요 없음
  2. 표준 라이브러리 `json`만으로 처리 가능
  3. 사람이 열어서 읽고 고칠 수 있음 (`ensure_ascii=False`로 한글 그대로 저장)
  - CSV는 내용에 쉼표·줄바꿈이 많아 다루기 불편하고, bool/int 타입 정보가 사라져서 선택하지 않았습니다.
- **안전 장치**: 임시 파일에 쓴 뒤 `os.replace`로 바꿔치기(저장 중 중단돼도 기존 파일 보존), 손상된 파일은 `.broken`으로 백업 후 기본 데이터로 시작,
  빠진 필드(`views` 등)는 기본값으로 채워서 예전 형식 파일도 읽을 수 있게 했습니다.

### 3-2. 같은 제목의 프롬프트가 여러 개 생긴다면? → 구현함

- **규칙**:
  1. 제목은 `normalize_title()`로 앞뒤 공백·연속 공백·영문 대소문자를 정리한 뒤 비교합니다 (`" 회의록  3줄 요약"` = `"회의록 3줄 요약"`).
  2. 추가·수정 시 같은 제목이 있으면 경고하고 **"그래도 저장할까요? (y/n)"** 를 묻습니다. 사용자가 원하면 허용합니다
     (예: 같은 제목으로 버전만 다른 프롬프트를 두고 싶은 경우).
  3. 프로그램은 제목이 아닌 **번호(목록 위치)와 내부 `id`** 로 프롬프트를 구분하므로, 제목이 같아도 수정·삭제·즐겨찾기가 섞이지 않습니다.
- 대안: 중복을 아예 막고 싶다면 `check_duplicate_title()`에서 `confirm` 대신 `False`를 반환하게 한 줄만 바꾸면 됩니다.

### 3-3. 병합 중 충돌이 나면?

1. **원인 파악**: `git status`로 충돌 파일 확인 → 파일의 `<<<<<<<`, `=======`, `>>>>>>>` 구간에서 양쪽 변경을 비교 →
   `git log --oneline --graph`, `git diff`로 각 브랜치가 왜 그 줄을 바꿨는지 확인합니다.
   (이 프로그램에서 가장 충돌이 잘 나는 곳은 여러 브랜치가 동시에 항목을 추가하는 `MENU_ITEMS` 목록입니다.)
2. **해결**: 한쪽을 버리지 않고 두 변경을 모두 살리도록 직접 합칩니다 (예: 양쪽에서 추가한 메뉴 항목을 둘 다 남기고 번호 정리).
   충돌 표시를 모두 지우고 `git add` → `git commit`으로 병합을 마칩니다. 판단이 어려우면 `git merge --abort`로 되돌리고 다시 시작합니다.
3. **검증**: `python3 -m unittest discover -s tests`로 테스트 실행, `python3 main.py`로 충돌 난 기능과 메뉴 전체를 직접 실행해 본 뒤 push합니다.

### 3-4. 카테고리 체계가 바뀌거나 늘어난다면?

- **수정할 곳은 `main.py` 상단의 `CATEGORIES` 목록 하나**입니다. 추가 화면(`choose_category`), 카테고리별 조회(`get_all_categories`),
  Markdown 내보내기가 모두 이 목록을 읽기 때문에 다른 코드를 고칠 필요가 없습니다.
- **추가**: 목록에 이름만 넣으면 됩니다. 선택 번호와 "직접 입력" 번호는 `len(CATEGORIES)`로 계산되므로 자동으로 맞춰집니다.
- **이름 변경·삭제**: 이미 저장된 `prompts.json`에는 옛 카테고리 이름이 남아 있습니다.
  `get_all_categories()`가 데이터에 있는 미등록 카테고리도 목록에 보여주므로 **기존 프롬프트가 사라지지는 않고**,
  필요하면 9번 수정 메뉴로 옮기거나, 불러올 때 `{"옛 이름": "새 이름"}` 대응표로 바꿔 주는 변환 단계를 `normalize_prompts()`에 추가하면 됩니다.
